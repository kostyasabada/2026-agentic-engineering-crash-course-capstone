# Implementation: add-realtime-chat-room-spec

## Task and criteria

Write the first OpenSpec change, `add-realtime-chat-room`, as planning artifacts only (no application code, no dependency installation, no commit). Criteria from the coordinator handoff:

- Artifacts created through the pinned OpenSpec CLI (`new change`, `status`, `instructions` for proposal, specs, design, tasks), following `.agents/skills/openspec-propose/SKILL.md` and the rules in `openspec/config.yaml`.

## Round 4

Input: checker review `review.md` round 3 (verdict `changes requested`: blocking B2, non-blocking N17–N21), relayed by the coordinator with the chosen fix, option 1 for B2. Same maker identity: Claude Code general-purpose subagent (maker). `review.md` was not edited.

### Findings and resolution

- **B2 (the DNS-rebinding claim was wrong): resolved with option 1, still Proposal P19.**
  - Design D2, P19 now checks the `Host` header of **every** HTTP request and upgrade in `server.ts` (pages and all engine.io traffic, including polling requests with an existing `sid`) against the own-host allowlist. A missing, unparsable, or foreign `Host` gets HTTP 403.
  - `allowRequest` additionally rejects a present `Origin` that is foreign, `null`, or unparsable. A missing `Origin` is accepted only because the `Host` check has already passed.
  - The DNS-rebinding explanation now matches browser behavior: same-origin GETs omit `Origin`, and they are refused by `Host`.
  - Residual risks are stated: local non-browser processes can connect with an allowlisted `Host`; LAN access only works if `HOST` names that address; the app is plain HTTP only.
  - Spec: the requirement is renamed "Local host and origin restriction" (it is a new capability, so renaming is allowed). The realistic rebinding scenario is a request with no `Origin` and `Host: evil.example:3000`, refused on both the polling and WebSocket transports, with no session, history, or sending. New scenario: a page request with a foreign `Host` is refused. The explicit foreign-Origin case is kept as a separate scenario.
  - Tasks: 4.2 adds red-first raw-HTTP tests covering both transports, `GET /`, the separate foreign-Origin case, null or unparsable Origin, accepted cases, and wildcard `HOST`, plus a manual `curl` with a foreign `Host` that must return 403. Task 4.1 unit-tests `src/server/host-policy.ts`.
  - Also updated: the D6 test description, the D4 layout (new module), the risks (a new entry for HMR and other host names), and the proposal wording.
- **N17 (wildcard HOST): resolved.** The spec requirement names the wildcard exception (`0.0.0.0`, `::`), with the scenario "Wildcard listen address adds no foreign hosts".
- **N18 (normalization): resolved.**
  - The design builds allowlist entries through `new URL("http://" + host + ":" + PORT)` and uses its `.host`/`.origin` (lowercase, default port omitted, IPv6 bracketed). Incoming values are normalized the same way.
  - The spec requires normalized comparison, with the scenario "Host comparison is normalized" (`LOCALHOST:<port>`).
  - Tests: uppercase and `PORT=80` in the 4.1 unit tests; `Host: LOCALHOST:<PORT>` in 4.2.
- **N19: resolved.** Task 0.1 explicitly says that P20 gates the chat-room spec's no-truncation rule and that P19 gates the Host/Origin mechanism; if either answer changes, the spec must be updated.
- **N20 (fingerprint robustness): resolved.**
  - Design D7: all three fingerprint commands use the pathspec `-- . ':(exclude)docs/evidence/<task-id>/loop-run.log' ':(exclude).agent-loop'`, so a committed log does not count as progress.
  - Untracked entries are hashed one by one: the `readlink` target for symlinks, SHA-256 for readable files, and the marker `unreadable:<path>` otherwise. The pipeline never fails, and it uses `xargs -0 -r` if `xargs` is used.
  - Task 1.4 adds tests: a broken symlink and an unreadable file do not abort the loop; retargeting the symlink counts as progress; a no-op fixer run with an already committed, appended `loop-run.log` still stops with `no_progress`.
- **N21 (wording): resolved.** `docs/architecture.md` now says the user "accepted" SQLite and local single-process deployment "as proposed and without objection".
