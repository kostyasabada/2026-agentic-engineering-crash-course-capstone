### Why these type package versions

- `@types/node` 24.19.0: the newest 24.x release. The project targets Node 24 (`engines.node ^24.0.0`, `.nvmrc` 24.21.0); the registry `latest` (26.6.3) would type APIs that Node 24 does not have. It satisfies the peer ranges of `vite` 8.3.1 (`^20.19.0 || >=22.12.0`) and `vitest` 5.0.2 (`^22.0.0 || >=24.0.0`), and all other packages that depend on `@types/node` dedupe to it.
- `@types/react` 19.3.0 and `@types/react-dom` 19.3.0: match React 19.3.0; `@types/react-dom` 19.3.0 has peer `@types/react ^19.3.0`.
- `@types/better-sqlite3` 9.6.0: needed because `better-sqlite3` 13.0.3 ships no `.d.ts` files (checked in the installed package, see `checks.txt`). 9.6.0 is the registry `latest`; no 13.x typings exist.

### Dependency placement reasoning

Rule: a package goes into `dependencies` if the running server (`npm start` = `NODE_ENV=production tsx server.ts`, design D5/P14) or the application source compiled by `next build` imports or executes it; tools used only for checking, typing, or testing go into `devDependencies`.

- `next`, `react`, `react-dom`: the custom server calls Next's request handler at runtime and renders React.
- `socket.io`: attached to the HTTP server at runtime (D2).
- `zod`: shared schema validated on the server at runtime (D4, P7, P11).
- `better-sqlite3`: message store at runtime (D3).
- `tsx`: `start` executes `server.ts` through `tsx` in production (P6), so it is a runtime requirement, not only a dev tool.
- `socket.io-client`: imported by the client chat code (`use-chat-socket.ts`, D4) and bundled by `next build`; it is application source input rather than a test tool, even though Node tests also use it. Placed in `dependencies` for that reason (bundling happens at build time, so `devDependencies` would also work technically; this is a convention choice).
- `typescript`, `eslint`, `eslint-config-next`, `@types/*`, `vitest`, `vite`, `@playwright/test`, `@fission-ai/openspec`: checking, typing, testing, and spec tooling only; `tsx` transpiles `server.ts` with esbuild, so TypeScript is not needed at runtime.

Consequence: `next build` type-checks and needs `typescript` and the `@types/*` packages when a `tsconfig.json` exists, so the build requires a full `npm ci` (with dev dependencies). This matches the local-only scope (no production image). Whether a runtime-only install (`npm ci --omit=dev`) can run `npm start` after a build was not verified here; nothing in the design requires it.

### better-sqlite3 native binding: prebuilt, not compiled

- The `better-sqlite3` 13.0.3 tarball itself contains prebuilt N-API binaries in `prebuilds/` (linux-x64, linux-arm64, linuxmusl-*, darwin-*, win32-*); it does not use `prebuild-install` or download anything.
- The process loads `node_modules/better-sqlite3/prebuilds/linux-x64.node` (read from `/proc/self/maps` after opening a database; see `checks.txt`).
- During `npm ci`, npm ran the package's implicit `install: node-gyp rebuild` (listed by `npm install-scripts ls`). Its `binding.gyp` checks for a matching prebuild (`node lib/binding.js` printed `1`) and then builds nothing: `build/Release/` contains only `.stamp` files and no `.node` file. No C++ compilation took place. (During the earlier `npm install` run no `build/` directory was created at all.)
